# Timeline Feed 系统设计（硬核课堂「系统设计」合集第 01-04 期）

## 学完你应该获得什么

1. 能区分 **Timeline Feed** 和 **Top K Feed**：前者按关注关系召回、按发布时间排序；后者按召回策略加推荐模型排序，两者的瓶颈和处理方式完全不同。
2. 能画出 Feed 系统的基本服务划分（User / Item / Feed / Relation / Comment / API），并说清一次「发布 → 分发 → 读取 → 进详情页」的完整链路。
3. 能解释**写放大**与**读放大**各自的时间复杂度、存储代价和分页难题，并知道什么时候必须放弃纯写放大。
4. 能讲清 **Lady Gaga 问题**引发的六个连锁反应，而不只是「大 V 粉丝多所以写不完」这一句话。
5. 掌握发布订阅侧的一整套优化手段：推拉结合、用户分级、冷热分离加预拉取、读写分离、写入补偿、流计算、持久化 KV，并知道每一招的收益与代价。
6. 掌握 Item（详情页）侧的延迟优化手段：并行 RPC、多级缓存、客户端预加载、Request backup、对象池、计数服务化（counter server）。
7. 掌握关系存储的分片选型：range 与 hash 分表的适用差异、按 from_user_id 还是 to_user_id 分片、单向关系的马太效应、双向关系的联合 hash。
8. 能把这套思路迁移到通知、动态、转评赞这类同样「一次写入、多次读取」的业务上。

## 一句话总论

Timeline Feed 的核心矛盾是**发 Feed 时的扇出成本**与**读 Feed 时的延迟**之间的取舍：写放大让读变快、写变贵且成倍浪费存储，读放大反过来；工业上的解法是按用户量级做分层，用推拉结合把写放大控制在可承受范围，再用缓存、补偿和持久化存储补齐延迟与可靠性。

## 适用场景与前置知识

**适合谁**：正在做或准备做信息流、订阅、通知、动态、转评赞计数的后端工程师；准备系统设计面试、需要一套完整论证而不是零散结论的人。

**需要先知道**：QPS、p99 延迟、可用性几个 9 的含义；Redis 常见数据结构和缓存穿透/击穿/热点问题的基本概念；MySQL 分库分表的思路；消息队列和 Flink 这类流计算组件的作用；收件箱（inbox）与发件箱（outbox）模型。

**不适合谁**：想学 Top K 推荐系统（召回、特征、排序、样本拼接）的读者——那是同一合集里的另一条线（推荐系统架构综述 01-03、实时样本拼接 01-03），本主题不覆盖。

## 核心概念卡

### Timeline Feed 与 Top K Feed

- **是什么**：Timeline Feed 按用户之间的关注关系召回 Feed，再按发布时间排序；Top K Feed 按召回策略取候选，再用推荐模型排序。
- **为什么重要**：两者决定了系统里「排序」这件事放在客户端还是服务端、以及延迟预算怎么分配。前者的延迟瓶颈在扇出与聚合，后者在模型推理与特征获取。
- **怎么用**：做信息流前先明确自己属于哪一类。关注关系驱动的就是 Timeline Feed，可以直接套用本主题的方案。
- **常见误区**：把 Timeline Feed 当成「简单版的推荐系统」，从而忽略了它在扇出和存储上的真实成本。[1]

### 收件箱（inbox）与发件箱（outbox）

- **是什么**：Feed 的存储按用户维度分成收件箱和发件箱两个 List。收件箱是「别人写给我的」，发件箱是「我写出去的」。收件箱里存的是 item ID，展示时再按 ID 聚合作者、内容、关系等信息。
- **为什么重要**：写放大就是把 item 写进粉丝的收件箱，读放大就是读自己关注的作者的发件箱。两者的取舍决定了整个系统的形状。
- **怎么用**：收件箱适合写少读多的普通用户；大 V 的发件箱适合被拉取。
- **常见误区**：评论区里有人问「inbox 是不是实际存在的数据结构，比如 Redis 的 zset，用户量大会不会很占资源」——它就是实际存储，容量成本正是后面「用户分级 + 冷热分离」要解决的问题。[1][11]

### 写放大与读放大

- **写放大**：发布 item 时查粉丝列表，把 item ID 写进每个粉丝的收件箱。写复杂度 O(粉丝数)，读复杂度 O(1)。读快、写慢、存储成倍浪费，必须异步。
- **读放大**：拉取时查自己的关注列表，逐个扇出读所有关注作者的发件箱，按时间戳合并取最新 20 条。读复杂度 O(关注数)，写复杂度 O(1)。写简单、省存储、读慢，而且**难以实现分页**。
- **为什么重要**：这是全篇的判断基准。任何优化方案都可以用「它把复杂度从哪一侧挪到了哪一侧、代价是什么」来评估。
- **常见误区**：以为读放大只是慢一点，实际上分页、去重、合规过滤都要在合并后的列表上做，工程复杂度远高于写放大。[1]

### Lady Gaga 问题

- **是什么**：DDIA 提出的场景。超级大 V 发布一条内容时，纯写放大方案会同时引爆六件事：① 一次 RPC 要拉千万级粉丝列表，500ms 内返回不了；② 千万次 RPC 无法在时限内完成，粉丝收到内容的时间差可达半小时以上；③ 大量点击涌入详情页，把详情页和它依赖的下游 QPS 一起拉高；④ 评论量激增，评论与评论数缓存的一致性受影响；⑤ 上热搜后大量关注行为压向关系服务，粉丝数与关注数缓存被频繁更新，可能引发缓存穿透；⑥ 全网转发引导大量注册，注册接口流量突增。
- **为什么重要**：它说明 Feed 系统的瓶颈从来不是单点，而是会被热点放大成系统性风险。
- **怎么用**：做容量评估时把「热点事件」当成必测场景，而不是只算平均 QPS。
- **常见误区**：以为限制粉丝数或者加机器就能解决。限制粉丝数会让产品功能受限，加机器解决不了「一次写一千万份」的存储浪费。[1]

### 推拉结合

- **是什么**：大 V 用拉模式（读放大），普通用户用推模式（写放大）。发布时，大 V 只写自己的发件箱，普通用户照旧扇出；读取时，先并行读自己的收件箱，再识别关注列表里哪些是大 V，去拉他们的发件箱，合并后返回最新的 Feed。
- **为什么重要**：这是把 Lady Gaga 问题压到可接受范围的关键一招，也是「读延迟略差于纯写放大、写延迟略差于纯读放大」的折中。
- **怎么用**：需要先有大 V 的识别能力（粉丝数、舆情热度、ML 打标，或用 Flink 流式识别发文行为），并且大 V 标签**只能升级不能降级**——一旦降级就要回溯所有粉丝的收件箱。
- **常见误区**：见下文「坑点」里关于「关注几千个大 V 会不会退化成几千次 RPC」的争论。[1][4]

### 缓存四件事：穿透、击穿、大 key、热 key

- **缓存穿透**：查询的 key 在缓存和 DB 里都不存在，请求反复落到 DB。讲稿给的是分布式锁加租约的做法：请求 A 发现为空，用 lua 写一个带租约的锁 key，B、C 自旋等待，A 查完 DB 回填缓存后释放，A 失败则租约到期自动过期。
- **缓存击穿**：热点 key 失效的瞬间大量请求打到 DB。做法是缓存空 key，并把空 key 单独放一个 cache 与有效 key 隔离，避免拉低命中率。
- **大 key**：String 类型 value 超过 10KB、集合类型元素超过 5000 个、集合单元素总长度超过 10MB 都算大 key，通过拆分 key 解决。
- **热 key**：用本地内存与磁盘缓存、双 TTL 机制缓解。
- **注意**：讲稿正文把「穿透」和「击穿」两个概念写反了，评论区有人指出过，需要按上面的定义校正。[1][6]

### Request backup（来自 The Tail at Scale）

- **是什么**：RPC 扇出时区分核心与非核心调用。非核心的可失败当作降级处理，核心的失败则主动取消所有无效下游请求；对核心 RPC 统计单机 p95，超时风险高的请求额外发一次 backup request 来对冲尾部延迟。
- **为什么重要**：这是把 p99 压下来的少数几个有效手段之一，代价是极端情况下给下游增加约 5% 的 QPS，开发复杂度也更高。
- **常见误区**：对所有 RPC 一视同仁地做重试，结果把下游打得更慢。[1]

### counter server（计数服务化）

- **是什么**：把点赞数、评论数、浏览数这类计数从 Item 服务里独立出来。写操作走 MQ 并做变更合并（生产端和消费端都可以合并），读操作把最热的 key 放在内存里；通过 MQ 保证恰好一次执行，实现计数的最终一致。
- **为什么重要**：Item 服务的读是延迟优先，计数写是吞吐优先，两者的负载特征互相矛盾，混在一起会同时拖累两边。
- **怎么用**：点赞这类操作可以「先在前端展示自己的点赞动作，底层异步达成最终一致」，评论则因为一致性要求最高，不适合用同一套折中方案。[1][8]

### 关系存储的分片选型

- **range 分表**：适合冷热差异明显的场景。关系数据的历史关注也会被频繁查询，不适合。
- **hash 分表**：按 from_user_id 分片，同一关注者的关注列表落在一个分片，查询关注列表最优；按 to_user_id 分片，粉丝列表查询最优。
- **马太效应**：单向关系（我关注你，你不关注我）下粉丝分布极度不均，所以应该按**粉丝维度**存储；双向关系没有马太效应，用 to_user_id 与 from_user_id 联合 hash 即可。
- **代价**：超级大 V 粉丝量过十亿时 hash 会让分片数据量不均；分库分表做不了在线 join，只能用周期备份到 hive 支持大规模分析查询，运维成本也高。[1]

## 方法或流程

### 发布一条 Feed 的完整链路

1. 用户发布 item → 写 Item 服务。
2. 调用 Relation 服务拿粉丝关系列表。
3. 触发一系列异步任务：审核、转码、NLP 打标签。
4. 异步把内容写入粉丝的收件箱列表，按时间戳（ts = timestamp）排序。
5. 大 V 走例外路径：只写自己的发件箱，不做扇出。

### 读取 Feed 列表的完整链路

1. 从 Feed 服务读自己的收件箱（写放大路径）。
2. 收件箱里只有 item ID，需要按 ID 去 Item 服务聚合作者、内容、与作者的关系等信息。
3. 识别关注列表里的大 V，并行拉他们的发件箱（推拉结合的拉模式部分）。
4. 合并、排序、执行过滤规则（有效性、合规性），再返回。

### 做这类系统设计时的判断顺序

1. **先算量级**：DAU、单条内容体积、读写比、峰值倍数。500M DAU 的参考数据是 Feed 列表接口 p99 ≤ 200ms、平均 60K QPS、峰值 90K QPS、5 个 9；一天新增存储约 1000TB，视频 CDN 出流量约 100PB。
2. **再定推拉**：普通用户推、大 V 拉，先把写放大的爆炸点去掉。
3. **再做分级**：大 V 按粉丝数分级，活跃用户按活跃度分级（如一月内活跃保留 100 条、周活跃 300 条、前一天活跃 500 条、日均多刷 1000 条），用存储换延迟。
4. **再补缓存与降级**：详情页走多级缓存、客户端预加载与 Request backup；计数走 counter server。
5. **最后兜可靠性**：收件箱写入失败走重试加补偿队列，保证最终一致；发件箱所在机器出问题时要有副本与读写分离。

## 关键洞察

- **事实描述**：Feed 系统是典型读多写少场景，读写比约 100:1；写放大复杂度 O(粉丝数)、读放大复杂度 O(关注数)。[1]
- **经验判断**：纯写放大在小 V 场景下最省事，但只要出现一个超级大 V 就会全局受影响，所以推拉结合是必要的，而不是可选项。[1][3]
- **推荐做法**：大 V 标签只升级不降级；收件箱长度按活跃度分级控制；计数与内容分离；核心 RPC 才做 backup request。[1]
- **限制条件**：推拉结合把复杂度推给了「大 V 识别」和「读取时的合并与分页」；分库分表换来规模却丢掉了在线 join；持久化 KV 替换 Redis 能降成本，但要让基础组件改造，研发成本高。[1][4]
- **可迁移的经验**：转评赞这类数据与关系存储同构——写吞吐要求高、读延迟要求低，用 KV 或图数据库较多，写可以先在前端展示、底层异步达成最终一致，与 counter server 思路一致。[8]

## 实践清单

- 容量评估时同时给出平均与峰值 QPS，并单列一条「热点事件」场景。
- 收件箱落地前先决定：存 item ID 还是存完整快照（存 ID 更省，但读取时要聚合，聚合失败要有降级）。
- 大 V 判定至少准备两条独立依据（粉丝数门槛、舆情热度或 ML 打标），避免边界抖动。
- 收件箱长度设上限，并准备「超过上限后退化为拉模式 + 预拉取」的路径。
- 缓存上线前先把穿透、击穿、大 key、热 key 四类的处理方式写进设计文档，而不是等出事故。
- 扇出调用区分核心与非核心，非核心的可失败直接降级；核心的用 p95 统计触发 backup request。
- 计数类接口独立成服务，写入合并、读取走向内存热点。
- 关系表确定分片键时先回答一个问题：这张表更常查关注列表还是粉丝列表；单向关系按粉丝维度分片。
- 用评论区里被问到的一个检查点自测：下架或不存在的内容被反复查询时怎么办——布隆过滤器有假阳性且要离线构建，本地缓存有一致性问题，全量 map 有内存问题，方案要能正面回答这三条。[1]

## 坑点与反例

- **讲稿里穿透与击穿写反了**：正文把「查询不存在的 key 导致请求打到 DB」与「热点 key 失效瞬间请求打到 DB」的定义写反了，评论区明确指出「教案里穿透和击穿的概念弄反了」。看这一节时按标准定义校正。[6]
- **第 03 期视频画面是镜像的**：评论区有人指出「TimeLine-3 的视频是镜像的，是不是压缩的时候出错了」，看画面时留意。[6]
- **正文里 item 被拼成 itme**：多处出现，评论区也提醒了，读的时候不要被带偏。[1][10]
- **「关注几千个大 V 会不会退化成几千次 RPC」的争论**：质疑方认为微博上关注上千人是常态，一次拉关注列表有上限，于是会变成几十次 RPC，既要拉内容又要聚合，还不好分页。UP 的答复是：这种情况基本不存在；查询会按 user id 分片，RPC 数量只与机器数量相关，类似 Redis 分布式场景下的 mget。评论区后来补充了几种思路：服务层提供批量拉取接口、存储层针对大 V 读缓存；也有读者提出先拉一批维护 TopK 缓存、客户端异步补拉、按 TTL 迭代的做法。这条争论很有价值，因为它把推拉结合真正难的地方暴露出来了。[4]
- **大 V 发件箱所在服务器宕机，会导致大 V 发布的 Feed 丢失**：这是推拉结合引入的新风险，讲稿把它列为该方案的风险项。[1]
- **大 V 降级要回溯全部粉丝收件箱**：所以设计成只能升级。[1]
- **图数据库存关系到底扛不扛得住**：UP 的答复是关系类数据用 KV 或图数据库较多，写吞吐要求高、读延迟要求低；有读者反馈实际项目里图数据库性能不佳，这一条没有在视频里给出定量结论，属于开放问题。[8]
- **下架或 404 内容的查询**：布隆过滤器假阳性在这个场景不可接受且要离线构建；本地化要考虑更新一致性；直接存 map 有内存压力。讲稿把这个问题留给读者讨论。[1]

## 自测题

1. Timeline Feed 和 Top K Feed 在召回与排序上的区别是什么？——Timeline 按关注关系召回、按发布时间排序；Top K 按召回策略取候选、用推荐模型排序。
2. 写放大和读放大各自的时间复杂度，以及各自最难受的地方是什么？——写放大 O(粉丝数)、读 O(1)，难受在存储浪费与写入延迟；读放大 O(关注数)、写 O(1)，难受在读延迟与分页。
3. Lady Gaga 问题会引发哪几类连锁反应？——写侧超时与顺序不一致、详情页与下游 QPS 抬升、评论系统压力与计数一致性、关注行为打爆关系服务缓存、注册流量突增，共六类。
4. 推拉结合里大 V 的判定依据有哪些，为什么只能升级不能降级？——粉丝数、舆情热度、ML 打标或 Flink 流式识别；降级需要回溯所有粉丝的收件箱，成本极高。
5. 收件箱长度为什么要按活跃度分级？——控制 Redis 内存与运维成本，把存储资源优先给真正会继续刷的活跃用户。
6. 缓存穿透和缓存击穿分别怎么处理？——穿透用分布式锁加租约（或缓存空 key），击穿用缓存空 key 并把空 key 与有效 key 隔离。
7. counter server 为什么要从 Item 服务里独立出来？——写操作吞吐优先、读操作延迟优先，两种负载特征矛盾，混在一起会互相拖累。
8. 单向关系按哪个维度分片，为什么？——按粉丝维度（to_user_id），因为单向关系存在马太效应，粉丝分布极不均匀。
9. 超级大 V 粉丝过十亿时 hash 分片会出什么问题？——分片数据量分布不均；讲稿也提示分库分表无法做在线 join，只能靠周期备份到 hive 做分析。
10. 如果让你现在设计一个「转评赞」系统，你会复用本主题里的哪些结论？——用 KV 或图数据库存关系类数据；写先在前端乐观展示、底层异步最终一致；计数独立成服务走 MQ 合并；评论单独处理，因为一致性要求最高。
