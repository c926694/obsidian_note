## Timeline Feed 系统设计

### 背景介绍

Feed 是一种承载信息的单元，feed 系统就是信息分发系统。信息分发是所有互联网应用的基本功能，也是其立身根本，淘宝/头条/抖音/微博等等 APP 都必须具有首页功能，首页通常用来展示 Feed 列表，信息分发承载着用户留存和商业化的重要目标，从技术上对延迟和可用性拥有极高的要求，每一次事故都会上热搜，了解 Feed 系统的设计对于后端工程师的成长是极为重要的。

Feed 系统通常有两个要素，召回和排序。召回决定有哪些 feed 应该分发给哪些用户；由于手机屏幕只有手掌大小，信息的展示位不足，所以必须要区分展示信息的优先级，因此就要有排序规则。根据这两点不同，通常可以分为 Timeline Feed 和 Top K Feed。

- Timeline Feed：根据用户与用户之间的关注关系来召回 Feed，然后基于发布时间排序的简单信息流系统。
- Top K Feed：根据某些召回策略召回 feed，然后基于推荐模型排序的复杂推荐系统。

本文讨论 Timeline Feed 系统的设计，目标不是面向面试的答题，而是程序员在实际工作中的落地思考。系统设计是开放性话题，有遗漏错误之处可直接评论。

为了避免侵权，我们以小视频的 feed 场景为参考，假设一款小视频微博：video_feed app。

### 设计目标

a. 用户发布一篇 Feed(item)（视频/文章/推文/微博/朋友圈等）
b. 用户关注其他用户 / 取消关注
c. 用户查看订阅频道，可以看到关注的用户发布的 Feed，以发布时间排序
d. 用户可以点击某个 feed，进入到当前 feed 的详情页面
e. 用户可以点击某个用户头像，进入到该用户主页面，展示他曾经发布的 Feed
f. 用户可以点赞、评论、转发一篇 Feed，用户的 feed 上也会展示标题/封面/点赞/评论/浏览数信息
g. 用户可以看到自己的收藏/点赞/浏览记录列表，并设置是否公开的权限
h. 合规安全性，不能放出非法内容，需要有审核机制

**存储容量**

假设一篇 feed 视频 2MB，则一天存储增量 2MB × 6K × 24 × 60 × 60 ≈ 1000TB。

**网络带宽**

网络请求的带宽可以忽略不计，但是视频 CDN 的带宽是巨大的，这里近似等于视频的大小 2M。用户一刷 10 条 Feed，小视频形式每刷都会点击，所以 CDN 消耗近似等于视频分发的量级：

10 条 × 60K × 2M × 24h × 60min × 60s ≈ 100PB。

**负载特性**

Feed 系统是一个典型的读多写少负载场景，通常为 100:1，一个用户发 feed，有 100 个用户会阅读此 feed。

### 方案设计

#### 初始方案

服务拆分，通过名词抽象为服务边界，接口为动词。

a. User server：存储用户信息，提供 CRUD 用户维度属性的能力
b. Item server：存储原始内容，提供发布和查询内容的能力
c. Feed server：存储 feed 信息，提供获取信息流列表的能力，个人主页/浏览记录/收藏列表等
d. Relation server：存储用户与用户的关系，关注/朋友等，获取粉丝列表、关注列表等
e. Comment server：存储评论数据，拉取评论列表，发布评论，获取评论数
f. API server：用来聚合用户请求，进行逻辑控制

#### 接口交互

**用户注册**：API server 调用 user server 鉴权/注册，用户信息写入 DB 即可。

**用户关注**：用户直接写接口即可。

**发布 Item**：
1. 用户发布 item 时，写 item 到 item 服务，然后调用 relation server 获得粉丝关系列表。
2. 触发一系列异步任务：审核、转码、NLP 打标签等等服务。
3. 异步将内容写入每个粉丝 user 的 inbox 列表中，并以 ts 做排序。

**读取 Feed 列表**：
1. 当用户获取 feed 列表时，直接从 feed server 读取该 user 的 inbox 即可。
2. inbox 中存储的是 item 的 ID，通过 item 的 ID 查询其作者/内容/与作者的关系等信息进行消息聚合。
3. 判断过滤规则，保证内容有效且合规后放出。

**点赞/收藏/评论/历史**：
1. API server 访问 item server 完成对 item 的点赞。
2. 访问 comment server 发布评论。
3. 将 item id 加入到 feed server 中对应 user 的收藏/历史列表中。

**点击详情页**：
1. 判断是否符合规则允许放出。
2. API Server 请求 item server 拿到 item 维度信息。
3. 通过其中的作者 userID，去 user 服务查询用户信息。
4. 通过 relation 服务查询该用户是否关注了作者。

#### Lady Gaga 问题

DDIA 中提出 Lady Gaga 问题，当 Lady Gaga 在发布一篇新的 twitter 时，上述系统将面对系统性瓶颈。

1. 发布 item 时获取粉丝列表，Lady Gaga 拥有千万粉丝，粉丝列表用 userID 的 size 就是 1000w，这导致一次 RPC 请求要从 relation server 中查询 1000w 的数据量，很难在 500ms 内返回；然后发布 item 时还需要向所有粉丝的收件箱中写入此 item ID，最坏情况会产生 1000w 次 RPC 调用，同时极其浪费存储空间，因为发布一篇 item 要将其存储 1000w 份。
2. 1000w 次 RPC 显然不能在 500ms 内完成，那么就会导致先写入成功的粉丝收到新的内容，后写入的粉丝滞后收到 feed，而第一个粉丝和最后一个粉丝可能相差半小时以上，用户体验受到严重影响。
3. 这一篇内容随后会产生大量的消费数据，粉丝们收到 feed 后大量点击阅读、进入详情页，使得详情页 QPS 拉高；详情页请求多种下游服务使得整体 QPS 都被拉高，如果此时服务资源容量不足将产生系统性崩溃，服务不可用。
4. 用户对此 item 非常感兴趣则会发生评论，评论系统压力大增，写入评论以及评论数等缓存的一致性受到影响。
5. Lady Gaga 的 item 上了热搜（热点洞察系统），被更多人看到后发生大量关注行为，对 relation server 的压力增加，同时对于粉丝数、关注数的缓存会被频繁更新，此时缓存可能造成缓存穿透等问题，导致关注系统崩溃。
6. 此热搜产生全网转发效应，引导更多人注册到 video_feed app，导致用户注册接口流量徒增成功瓶颈。

#### 读放大与写放大问题

Feed 的存储按用户维度具有收件箱和发件箱两个 List。

**读放大**
1. 当拉取 feed 时，查询自身关注列表，然后逐一扇出请求所有关注作者的发件箱内容中未阅读过的 item（通过记录上一次拉取的时间戳实现）。
2. 拿到多个 item ID 后通过时间戳对其进行排序，得到一个 list，从中取 20 条最新结果返回。
3. 对返回的 item ID 进行打包（聚合展示信息）、过滤等逻辑，然后生成最终展现的 feed 列表。

读的时间复杂度是 O(关注数)，写复杂度是 O(1)。写逻辑实现简单，节约存储，读性能差，难以实现分页功能。

**写放大**
1. 当发布 item 时，查询作者的粉丝列表，并将发布的 item ID 写入粉丝的收件箱。
2. 读取时直接读取自身的收件箱，然后打包 item 信息组织成 feed 进行展示。

写的时间复杂度是 O(粉丝数)，读的复杂度是 O(1)。浪费存储，读性能好，写性能差，需要异步。

#### 2. Item Server 优化：延迟 & 可用 & 存储优化

Item server 主要提供查询和发布 item 的能力，是一个读写比大于 100:1 的在线服务。随着规模增长，哪些场景会成为性能瓶颈？首先是 item 详情的查询：item 详情需要聚合大量下游数据，扇出调用多个 RPC 去聚合多个 server 的内容，并且要判断某些内容是否已经不合规被下架、是否为 404 查询等等问题。

| 方案 | 收益 | 风险 |
| --- | --- | --- |
| **1. 并行调用下游 RPC；2. 检查 item 状态为不可见则直接拒绝请求；3. 拿到数据后将数据组织打包后返回** | 实现简单，QPS 在 5k 左右没有问题 | 1. 没有区分核心路径，关键 RPC 失败后其他 RPC 可直接终止；2. 查询路径过长，经过多次 RPC 跳转，延迟不稳定；3. 延迟高，打开速度慢 |
| **使用缓存**（命中率关键）：1. 本地缓存解决高热问题；2. 分布式缓存解决容量问题；3. 基于 TTL/旁路缓存/基于事件驱动删除 key 来更新缓存；4. 通过分布式锁解决缓存穿透问题；5. 通过缓存空 key 解决缓存击穿问题（为避免大量空 key 导致命中率下降，空 key 的缓存可以单独维护一个 cache 与有效 key 隔离）；6. 通过拆分 key 解决大 key 问题；7. 通过本地（内存 & 磁盘）缓存/双 TTL 机制解决热 key 问题。<br>分布式锁要点：① 请求 A 查询 key1 发现为空，通过 lua 设置一个 key1: lock_[id]_[ts] 的租约；② 请求 B、C 查询时发现 key1 有锁，则直接自旋一下；③ 请求 A 拿到租约后查询 DB，获得数据后更新 key1 的 value；④ 请求 B、C 自旋查询后再次尝试读取 key1，得到数据后返回；⑤ 如果请求 A 读取数据失败，则租约到期后自动过期；⑥ 请求 B、C 谁先请求谁将获得锁再次执行上述流程。<br>多大算大 key？① String 类型 value 长度超过 10KB；② 集合类型元素个数不超过 5000 个；③ 集合类型单元素总长度不超过 10MB | 1. 缩短查询路径，使延迟更加稳定，通过提高缓存容量可以提高缓存命中率；2. 通过高缓存命中率换来低延迟、高可靠 | 缓存过多，内存成本怎么取舍？ |
| **客户端预加载**：1. 对于详情页内容，在客户端屏幕展示 feed 时就同步请求详情页，预加载到本地，当用户点击后直接放出；2. 进一步优化，多请求超过屏幕展示条数的 feed 内容并在内存中缓存，异步去请求详情页进行缓存；3. 当用户停留在某个 feed 超过一定时长后进行预加载，减少一部分无效请求 | 预加载使延迟降到最低 | 1. 增加了很多无效请求；2. 需要不断优化预加载策略才能使效果最大化 |
| **使用持久化 KV 引擎、持久化内存、SSD 等新硬件降低内存使用成本** | 降低内存存储成本 | 需要对基础组件进行改造，研发成本高 |
| **Request backup 降级策略**（参考《The Tail at Scale》论文精读）：1. RPC 扇出请求，但并不是每个 RPC 都同等重要，有一些 RPC 可失败，有一些不可以；2. 对于可失败的 RPC 当作降级处理，对于不可失败的 RPC 一旦失败则主动取消所有无效下游请求；3. 对于核心 RPC 通过统计单机 p95 发起 backup request 来进行超时风险的对冲，降低整体 p99 延迟 | 1. 通过对 RPC 的限制提高了可用性；2. 降低了 p99 延迟 | 1. 需要复杂的开发过程；2. 极端情况下为下游增加 5% QPS |
| **核心对象池，降低 GC 影响**（降低后台任务对在线服务 p99 的影响）：1. Web server 会创建非常多的同类小对象，这类对象生命周期通常是一次请求内；2. 使用 tcmalloc 或 jemalloc 内存分配器提高内存分配性能，然后在业务层对小对象建设对象池；3. 对象使用后被回收到对象池中，对象池持有对象，进而不会被 GC 回收（最好想办法关闭 GC，或者使用堆外内存） | 1. 减少 GC 影响，业务侧自行管理内存分配，自主权更高；2. 延迟更稳定 | |
| **计数操作服务化 - 抽象 counter server**：1. 写操作吞吐优先，而读操作延迟优先，这与 item 的工作负载相互矛盾，因此拆解出独立服务用于资源隔离；2. 对于写操作可以使用变更合并策略，在生产端与消费端都可以实现合并，减少 RPC 的网络调用，提高吞吐量；3. 对于 counter server 的读取，直接将高热的 key 存储在内存中，以提供最大限度的低延迟查询；4. Counter server 通过 MQ 保证恰好一次执行，并实现计数值的最终一致性 | 1. 解决了 count 与内容本身的一致性问题；2. 对写操作进行了吞吐优化；3. 较折中地解决了低延迟、高吞吐、最终一致性、可用性等问题 | 实现起来更加复杂，研发成本更高 |
