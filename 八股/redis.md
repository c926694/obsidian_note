# 基础概念

## Redis 为什么快

**一、内存操作

```
磁盘寻址：约 10ms
内存寻址：约 100ns
              差 10 万倍
```

持久化（RDB/AOF）不阻塞主流程：RDB fork 子进程写，AOF 追加写文件+异步刷盘。

**二、单线程模型

6.0 之前网络 IO 和命令执行都是单线程。

**好处**：没有**锁竞争**、**上下文切换**

**代价**：只能用一核，所以 Redis 瓶颈在**网络 IO 和内存带宽**，不在 CPU。

6.0 之后引入多线程处理网络 IO，但命令执行仍然是单线程。

**注意**：单线程下执行慢命令（`KEYS *`、大 key 的 `HGETALL`）会阻塞整个 Redis。

**三、多路 IO 复用（重点）**

**对比理解**

```
传统 BIO：
线程1 ── read() ── 等数据 ── 被挂起
线程2 ── read() ── 等数据 ── 被挂起
N 个连接 = N 个线程，几千就撑不住了

Redis epoll：
主线程：epoll_wait() ← 内核通知哪些 FD 有数据
        → 只处理有数据的 FD → read() → 执行 → write()
        → 回到 epoll_wait()
10 万连接 → epoll 只返回有数据的几个 → 只处理这几个
```

| | BIO | epoll（Redis） |
|--|-----|---------------|
| 等待方式 | 每连接一个线程阻塞 read | 一个线程等 epoll 通知 |
| 连接数 | ~几千 | 10 万+ |
| CPU 利用 | 线程切换浪费大量 CPU | 只处理有数据的连接 |

**平台差异**：Linux 用 epoll、macOS 用 kqueue、Solaris 用 evport，统一封装在 ae 事件循环里。

**四、数据结构优化**

| 结构     | 底层实现                       | 为什么快                   |
| ------ | -------------------------- | ---------------------- |
| String | SDS（Simple Dynamic String） | 存长度字段，取长度 O(1)；自动扩容防溢出 |
| List   | quicklist（压缩链表+双向链表）       | 内存紧凑，减少碎片              |
| Hash   | dict + ziplist（小数据）        | 小数据连续内存，cache 友好       |
| Zset   | skiplist（跳表）               | 范围查询 O(logN)，实现简单      |
| Set    | intset + dict              | 小整数连续数组，省内存            |
|        |                            |                        |

**为什么 Zset 用跳表不用平衡树**：跳表实现简单，范围查找不需要中序遍历，内存中比树更 cache friendly。

## epoll 

实现一个线程高效知道哪些连接有请求过来
**一、没有 epoll 之前的两条路都走不通**

**阻塞 IO + 每连接一线程**：10 万连接 = 10 万线程，线程栈 + 上下文切换爆炸，瓶颈在"线程数量"。

**非阻塞 IO + 自旋轮询**：每轮 O(n) 挨个检查 fd 有没有数据，10 万次检查全浪费在"问"上，瓶颈在"扫描复杂度"。

**二、epoll 的做法：把监听从用户态交给内核态**

```
用户注册关心的 fd（epoll_ctl）
↓ 内核红黑树存 fd，有事件的挂进就绪链表
epoll_wait() 直接返回就绪链表（只有几个）
↓ 只处理这几个，O(1) 拿到结果
```

关键：用户不再挨个问，内核主动通知"哪些就绪"，监听成本 O(n) → O(1)。

**三、select / poll / epoll 对比**

| | select | poll | epoll |
|--|--------|------|-------|
| fd 数量限制 | 1024（FD_SETSIZE） | 无 | 无（百万级） |
| 每次调用 | 全量拷贝 fd 集合 | 全量拷贝 fd 集合 | 内核维护，零拷贝 |
| 扫描复杂度 | O(n) | O(n) | O(1) |
| 通知方式 | 靠扫描 | 靠扫描 | 就绪链表通知 |

**一句话记忆**：select/poll 是"用户挨个问"，epoll 是"内核主动通知"；前者 O(n)，后者 O(1)。

**五、6.0 多线程 IO（不是 epoll 变多线程）**
多个线程都设置epoll_wait,内核可以通知多个线程,利用cpu核数

```
6.0 前：epoll_wait → read → 执行命令 → write（全在主线程单线程）
6.0 后：epoll_wait（仍单线程）→ IO 线程池并行 read / write
        命令执行：仍是主线程单线程
```

| 环节             | 6.0 前 | 6.0 后    |
| -------------- | ----- | -------- |
| epoll 监听       | 单线程   | 单线程（没变）  |
| read/write 搬数据 | 主线程   | IO 线程池并行 |
| 命令执行           | 单线程   | 单线程（没变）  |

## Redis 支持的数据类型

**5 大基础类型**

| 类型 | 底层结构 | 核心特点 | 常用命令 | 典型场景 |
|------|---------|---------|---------|---------|
| String | SDS | 最基础，value 最大 512MB | SET / GET / INCR / EXPIRE | 缓存、计数器、分布式锁、Session |
| List | quicklist | 双向链表，两端操作 O(1) | LPUSH / RPUSH / LPOP / BRPOP | 简单消息队列、最新列表、时间线 |
| Hash | dict + listpack | 存对象，field 级操作 | HSET / HGET / HGETALL | 对象缓存（用户、商品信息） |
| Set | intset + dict | 元素唯一、无序、集合运算 | SADD / SISMEMBER / SINTER / SUNION | 去重、共同好友、标签、抽奖 |
| Zset | skiplist + dict | 按 score 排序，范围查询 | ZADD / ZRANGE / ZRANGEBYSCORE | 排行榜、延迟队列、滑动窗口限流 |

**3 大特殊类型**

| 类型 | 本质 | 核心特点 | 典型场景 |
|------|------|---------|---------|
| Bitmap（位图） | 就是 String 的位操作 | 1 bit 存一个状态，极省内存（10 亿人签到约 125MB） | 签到、在线状态 |
| HyperLogLog | 去重计数算法 | 计数 2^64 个元素只需 12KB，误差 0.81%，非精确 | UV 统计 |
| GEO | 底层 Zset + geohash 编码 | 存经纬度，支持距离计算、范围查找 | 附近的人、距离排序 |

**高级类型**

| 类型 | 说明 | 场景 |
|------|------|------|
| Stream（5.0 引入） | 专为消息队列设计：消费者组、ack 确认、持久化、顺序保证 | 真正的消息队列 |

**易混点**

- List 队列 vs Stream 队列：List 弹出即删，消费者挂了消息丢失、无确认；Stream 有 ack + 消费者组 + 持久化
- Bitmap 没有独立结构：就是 String，用 SETBIT / GETBIT 按位操作
- GEO 没有独立结构：底层是 Zset，score 存 geohash 编码
- HyperLogLog 有误差（0.81%），精确计数用 Set 或 DB
- Zset 底层 = skiplist + dict：跳表做范围查询，dict 做 O(1) 按 member 查 score

**时间复杂度速查**

| 类型          | 增                  | 删                | 单点查                         | 范围查                       |
| ----------- | ------------------ | ---------------- | --------------------------- | ------------------------- |
| String      | O(1) SET           | O(1) DEL         | O(1) GET                    | 无                         |
| List        | O(1) LPUSH / RPUSH | O(1) LPOP / RPOP | O(N) LINDEX                 | O(N) LRANGE               |
| Hash        | O(1) HSET          | O(1) HDEL        | O(1) HGET                   | O(N) HGETALL（N = field 数） |
| Set         | O(1) SADD          | O(1) SREM        | O(1) SISMEMBER              | O(N) SMEMBERS / SINTER    |
| Zset        | O(logN) ZADD       | O(logN) ZREM     | O(1) ZSCORE / O(logN) ZRANK | O(logN+M) ZRANGE，M = 返回数  |
| Bitmap      | O(1) SETBIT        | O(1)             | O(1) GETBIT                 | 无                         |
| HyperLogLog | O(1) PFADD         | 无                | O(1) PFCOUNT                | 无                         |
| GEO         | O(logN) GEOADD     | O(logN) ZREM     | O(logN) GEOPOS              | O(N+logM) GEOSEARCH       |
| Stream      | O(1) XADD          | O(1) XDEL        | O(logN)                     | O(logN+M) XRANGE          |

**复杂度要点**

- Hash 的 HGETALL 是大 key 慢命令：field 上万时阻塞整个 Redis，改用 HSCAN 渐进遍历
- List 的 LINDEX O(N)：别拿 List 当数组做随机访问
- Set 集合运算（SINTER / SUNION）O(N)：集合巨大时全量计算很慢
- Zset 单点 O(1)（dict）+ 范围 O(logN+M)（skiplist）→ 排行榜场景快的根本原因
- 范围查几乎都是 O(logN+M)：**M 是返回条数，分页限制 M 比优化 N 更重要**

# 缓存

## 缓存穿透

**定义**：查询一个**根本不存在的数据**——缓存没有，DB 也没有。每次请求都绕过缓存直接打到数据库，恶意攻击者专挑这种 key 打，能把 DB 打挂。

```
正常请求：Redis 有 → 直接返回
          Redis 无 → 查 DB → 有 → 回填缓存
穿透请求：Redis 无 → 查 DB → 无 → 没有东西可回填
          → 下次再来 → 还查 DB → 每次都穿透
```

**产生原因**：
1. 业务 bug / 用户传错参数：查了不存在的 id
2. 恶意攻击：批量用不存在的 key 打接口（负数 id、随机字符串、越界 id）
3. 缓存没有兜底：查不到就不缓存 → 同一个不存在的 key 每次都穿到 DB

**本质**：缓存只对"存在的数据"有效，不存在的数据每次都要落 DB。

**四种解决方案**：

**方案 1：缓存空值**（最简单、最常用）
- 做法：DB 查不到时也写空值（null / 特殊标记）+ 短 TTL（如 5 分钟）
- 优点：实现简单，一次穿透后后续请求全走缓存
- 缺点：占内存；空值期间数据真实出现会短暂读不到（可接受）

**方案 2：布隆过滤器**（治本，拦截在缓存之前）
- 做法：合法 key 全集（所有用户 id）预载入，请求先过过滤器，**不存在直接拒绝**，不碰缓存和 DB
- 特点："一定不存在" 100% 准；"存在"有误判率（宁错杀不放过）
- 缺点：维护 key 全集成本，新增 key 需同步
- 适用：key 集合相对固定（用户 id、商品 id）

**方案 3：参数合法性校验**（事前拦截，成本最低）
- 做法：id 格式不对、负数、超范围，直接拒绝，连 Redis 都不发
- 缺点：拦不住"格式合法但不存在"的 id，做第一道防线

**方案 4：限流 + 监控兜底**（最后防线）
- 做法：监控缓存命中率、DB 异常查询量，发现攻击对该 IP / 接口限流熔断
- 缺点：被动防御

## 缓存击穿

**定义**：**热点 key 在过期的那一刻**，大量并发请求同时发现缓存没有 → 同时打到 DB。和穿透的本质区别：**key 是真实存在的，只是恰好过期了**。

```
热点 key（如秒杀商品）过期瞬间：
请求1：缓存 miss → 查 DB
请求2：缓存 miss → 查 DB
请求3：缓存 miss → 查 DB
... 上万个请求同时回源 → DB 瞬间被打垮
```

**产生原因**：
1. 热点 key 的 TTL 到期，缓存失效
2. 该 key 正在被高并发访问（热搜、爆款、秒杀品）
3. 缓存重建（回源）没有串行化——所有请求各自去查 DB

**本质**：**缓存重建没有互斥**，一个 key 的失效引发瞬时并发全部穿透到 DB。

**解决方案**：

**方案 1：互斥锁**（保证重建只发生一次）
- 做法：缓存 miss 后先抢分布式锁（`SET NX EX`），抢到的线程查 DB + 回填缓存；抢不到的**自旋重试**（或短暂等待后重读缓存）
```
GET cache → miss
SET lock NX EX 3s → 失败 → 自旋：重试 GET cache（大概率已回填）
                  → 成功 → 查 DB → 回填 → 释放锁
```
- 优点：实现直接，同一时刻只有一个请求打 DB，效果可靠
- 缺点：有锁等待；锁必须设过期时间防死锁；多机部署要用**分布式锁**
- 适用：对一致性要求高的场景

**方案 2：热点 key 永不过期**（逻辑过期）
- 做法：**不设物理 TTL**，value 里额外存一个"逻辑过期时间"字段；读取时发现逻辑过期 → **返回旧值 + 异步线程去更新缓存**
- 本质：缓存**永远有值**，请求永远不 miss，自然永远打不到 DB
- 优点：没有"缓存空窗期"，请求永远有数据返回，性能最好
- 缺点：数据短暂不一致（可能读到旧值）；需要后台异步任务负责刷新
- 适用：热搜榜、商品详情这类"旧值可接受、并发极高"的热点数据

**方案 3：singleflight（请求合并 / 单飞）**
- 做法：进程内按 key 合并——同一 key 的并发请求**只放行一个**去查 DB，其他请求**直接共享第一个请求的结果**（挂起等结果，拿同一份数据）
- 实现：Go 的 `golang.org/x/sync/singleflight`，`g.Do(key, fn)`
- 和互斥锁的区别：互斥锁是"等锁释放后**重读缓存**"；singleflight 是"**直接复用结果**"，省一次缓存重读
- 缺点：**进程内**有效——单实例 OK，多实例部署每个实例各合并各的，跨实例仍需分布式锁
- 组合拳：本地 singleflight 合并 + 跨实例分布式锁兜底
- 适用：高并发热点 key 重建、DB 热点查询合并

**补充：热点预热**（配合用）
- 定时任务在 key 过期**之前**提前刷新，让 TTL 永远续着，从源头避免过期瞬间

## 缓存雪崩

**定义**：**大量 key 在同一时刻集中过期**（或 Redis 宕机导致缓存整体失效），所有请求同时绕过缓存打到 DB，DB 被压垮。

```
正常：key1 过期 → key2 过期 → key3 过期（错峰，每时刻只有少量失效）
雪崩：key1 key2 key3 同一时刻全部过期
      → 上百万请求同时打 DB → DB 崩了
```

**产生原因**：
1. 大量 key 设置了相同的过期时间（如缓存统一 1 小时，整点全过期）
2. Redis 宕机 / 重启：缓存整体不可用，所有请求直接落 DB（比 key 过期更严重的雪崩）

**解决方案

**事前（预防为主）**：
1. **过期时间加随机值**（最核心一招）：TTL = 基础值 + 随机值（如 1h + random(0, 10min)），key **错峰过期**
2. 热点数据永不过期（逻辑过期，异步刷新）
3. 多级缓存：本地缓存 + Redis 两级，Redis 挂了本地还能扛一阵
4. 高可用架构：主从 + 哨兵 / Cluster，宕机自动切换，缩短整体不可用窗口

**事中（保 DB 不死）**：
1. 限流 + 熔断：对 DB 访问限流，超阈值直接降级返回
2. 互斥锁 / singleflight：防止同一时刻百万请求同时重建缓存
3. 服务降级：返回默认值 / 兜底数据

**事后（恢复期）**：
1. Redis 持久化（RDB / AOF）：重启后快速恢复，避免冷启动全部 miss
2. 错峰重建：逐步回填缓存，防止恢复瞬间再次集中打 DB
3. 监控告警 + 复盘：命中率 / QPS / DB 连接数监控，命中率骤降即告警

## Redis 大 key

**判定标准**：
- String：value > 10KB
- Hash / Set / Zset / List：元素 > 5000 个，或总内存 > 10MB

**危害**：
1. 慢命令阻塞：HGETALL / SMEMBERS / LRANGE 0 -1 在大 key 上是 O(N)，单线程下卡住整个 Redis
2. 删除 / 过期也阻塞：DEL 大 key 是同步删除，O(N) 释放内存，主线程照卡
3. 网络传输慢：大 value 序列化 + 传输占带宽
4. 内存倾斜：集群下大 key 全落一个节点，该节点内存爆，其他节点空闲
5. 持久化拖累：RDB 写盘、fork 时大 key 都是开销

**怎么发现**：
- `redis-cli --bigkeys`：在线扫描不阻塞，直接给 Top 大 key
- `MEMORY USAGE key`（4.0+）：精确查单 key 内存
- 慢日志：SLOWLOG 里频繁出现 HGETALL / SMEMBERS 全量命令就是信号

**解决方案（核心 = 拆分）**：

| 拆分方式 | 做法 | 适用 |
|---------|------|------|
| 拆 value | 大 JSON 拆字段改用 Hash | 大 String |
| 分桶（hash tag） | `key:{0..99}`，field % 100 路由 | 大 Hash / 大 Set |
| 拆时间 | `feed:20260801` 按天拆 | 大 List / 大 Zset |
| 拆集合 | 按业务前缀 / 类别拆 | 大 Set |

# 缓存与数据库一致性

0## 为什么会有不一致

同一份数据存在两份（缓存 + DB），**更新做不到原子性**——总有一个先一个后，中间窗口期读到的就是旧值。

**核心思路**：读走 Cache Aside（先读缓存，miss 查 DB 回填）；写**先更新 DB，再删缓存**（不是更新缓存）。

**为什么写操作"删缓存"而不是"更新缓存"**：
1. 并发覆盖：线程 A、B 同时写，DB 里 B 后写（B 新），缓存却可能被 A 的旧值覆盖 → 永久不一致
2. 写多读少浪费：每次写都更新缓存，很多值根本没被读过，白写
3. 删缓存 = 惰性加载：下次读 miss 时回填新值，天然最终一致

## 策略

1. Cache Aside 基础版

```
写：更新 DB → 删缓存
读：读缓存 → miss → 查 DB → 回填缓存
```

**问题**：删缓存这一步可能失败。更新 DB 成功、删缓存失败 → 缓存永远旧值 → 直到缓存过期或下次更新才纠正，属于**永久不一致**（不是短暂）。

2. 延迟双删（Double Delete）

**顺序固定：删 → 改 → 等 → 删**（第一次删除在更新 DB **之前**，不能反过来）

```
第 1 次删缓存（更新 DB 之前，让旧值先失效）
    ↓
更新 DB
    ↓ 延迟 500ms~1s（等读线程把旧值回填完）
第 2 次删缓存（清掉窗口期回填的旧值）
```

**为什么第一步必须"先删缓存"而不是"更新 DB 后删两次"**：
1. 第一次删除必须在更新 DB **之前**，让旧缓存立即失效
2. 更新 DB 期间，读请求 miss → 查 DB 拿到**旧值** → 回填旧值（就是要防的窗口）
3. 延迟后的第二次删除：清掉窗口期回填的旧值
4. 反例：先更新 DB 再删，更新完后读请求回填的就是**新值**，第二次删除没有清理目标，白删

**解决什么竞态**：

```
线程A：更新 DB（新值）
线程B：读缓存 miss → 查 DB（旧值，A 还没提交）→ 回填缓存（旧值）
→ 缓存里是旧值，可能长期存在
```

第二次删除把 B 回填的旧值删掉，下次读再回填新值。

**要点**：
1. 延迟时间必须 > 读线程回填耗时（一般 500ms~1s，视业务而定）
2. 第二次删除也可能失败 → 仍需重试兜底
3. 只能保证**最终一致**，不是强一致

3. 删除失败重试（保证删除一定成功）

| 方式 | 做法 |
|------|------|
| 同步重试 | 删除失败立即重试 N 次 |
| MQ 异步重试 | 删除失败把 key 发到 MQ，消费者重试 |
| 本地消息表 | 删除失败记本地表，定时任务扫表重删 |

4. 订阅 binlog 异步删除（Canal，最推荐）

```
应用：更新 DB
MySQL：写入 binlog
Canal：伪装成 slave 订阅 binlog
→ 解析出变更 → 发 MQ
→ 消费者删除对应缓存（失败重试）
```

**本质**：把"删缓存"从业务同步流程剥离，交给独立的 binlog 消费链路——业务只管 DB 不写删缓存逻辑，重试在消费端做。

5. 加锁串行化（强一致）

1. 读写加同一把锁，写期间读阻塞 → 永远读不到中间态
2. 适用：一致性要求极高、写极少、性能要求不高的低频场景

## 方案对比

| 方案              | 一致性           | 复杂度 | 性能影响     | 适用场景             |
| --------------- | ------------- | --- | -------- | ---------------- |
| Cache Aside 基础版 | 低（删失败即长时间不一致） | 最低  | 无        | 能容忍删失败（有 TTL 兜底） |
| 延迟双删            | 最终一致          | 低   | 极低（两次删除） | 读多写少的常规业务        |
| MQ / 本地表重试      | 最终一致          | 中   | 低        | 删除失败不可容忍         |
| Canal 订阅 binlog | 最终一致          | 高   | 无（异步旁路）  | 大型系统、不想侵入业务代码    |
| 加锁串行化           | 强一致           | 低   | 高（读被阻塞）  | 一致性要求极高的低频场景     |

## 先更新 DB 再删缓存 vs 先删缓存再更新 DB

**结论：业界推荐"先更新 DB 再删缓存"，不一致窗口更小、更可控。**

**先更新 DB 再删缓存（Cache Aside）**

```
更新 DB → 删缓存
```

**优点**：
1. 正常路径一致性最好：删成功后，下次读必然是新值
2. 竞态窗口**极小**：唯一危险场景是"缓存恰好过期"的瞬间
3. 删除几乎不会失败（Redis 删不存在的 key 也返回成功），失败是小概率

**缺点**：
1. **删除缓存失败 → 长期不一致**：DB 已更新、缓存旧值，只能等 TTL 过期或下次更新（补救：删除失败重试 / Canal 兜底）
2. 极小概率竞态（三个条件同时满足才触发）：

```
线程A：读缓存 miss（缓存刚好过期）→ 查 DB（旧值）→ 网络慢
线程B：更新 DB → 删缓存
线程A：回填旧值 → 缓存长期旧值
```

**先删缓存再更新 DB**

```
删缓存 → 更新 DB
```

**优点**：
1. 顺序直观：先让旧值失效，再改数据
2. 更新 DB 失败无副作用：缓存已删，下次读重新回填旧值，不会不一致

**缺点**：
1. **竞态窗口大**：删缓存到 DB 更新完成之间（整个更新耗时，毫秒级），**每次**读请求都会回填旧值：

```
删缓存 → 读 miss → 查 DB（旧值，DB 还没更新）→ 回填旧值
       → DB 更新完成 → 缓存旧值 → 不一致
```

2. 每次写操作都有概率触发，比"先更新再删"的竞态概率大得多
3. 补救要上延迟双删，复杂度更高

**对比表**

| 对比项 | 先更新 DB 再删 | 先删缓存再更新 DB |
|--------|---------------|------------------|
| 不一致窗口 | 删缓存失败（小概率）或缓存恰过期瞬间（极小概率） | 整个 DB 更新耗时，每次写都有概率 |
| 补救方式 | 删除失败重试 / Canal | 延迟双删 |
| 工程结论 | **推荐** | 需要额外补偿 |

**一句话**：两者都做不到原子，但"先更新再删"把不一致概率压到最低——删缓存失败是小概率且可重试补救，"先删再更"的窗口是每次写操作都存在的结构性缺陷。

## 延迟双删策略原理

**一句话**：对"先删缓存再更新 DB"方案的补偿——等读线程把旧值回填进缓存之后，再删一次，清掉旧值。

**为什么需要延迟，而不是更新完立刻删第二次**：
1. 读线程回填旧值是**异步且慢**的：先查 DB（拿到旧值）再写缓存，中间有网络耗时
2. 立刻删第二次可能删在回填**之前**——旧值还是活了，白删
3. 必须 sleep 到"所有并发读线程都回填完"之后再删，第二次删除才有意义

**延迟时间怎么定（核心推导）**：
1. 必须 > 读线程"查 DB + 回填缓存"的最长耗时（一般 500ms~1s，视网络状况）
2. 太短：旧值回填在第二次删除之后，白删
3. 太长：不一致窗口被人为拉长（期间读到的还是旧值）

**本质**：延迟双删不是消除不一致，而是把不一致的**持续时间压到一次回填周期内**——最终一致。

**局限**：
1. 第二次删除也可能失败 → 仍需重试兜底（和方案 3、4 组合用）
2. sleep 是同步阻塞，用延迟队列 / 异步任务代替，别阻塞主线程
3. 只补偿"先删后更"的窗口；"先更后删"方案不适用（见上节对比）

## 如何保证强一致性？Canal 订阅 binlog 方案

**先说结论（面试先抛）**：缓存和 DB 之间**没有真正意义的强一致**——"更新 DB"和"删缓存"无法原子完成，任何方案都只能做到**最终一致**。Canal 方案的目标不是"强一致"，而是把不一致的**概率和持续时间降到最低**，可靠性最高。

**完整链路**：

```
应用：更新 DB（业务代码只管这一步）
    ↓
MySQL：写入 binlog（事务提交时同步写，保证不丢）
    ↓
Canal：伪装成 MySQL slave 订阅 binlog，解析出变更（表、主键、类型）
    ↓ 发送到 MQ
MQ：消息持久化
    ↓ 消费（成功才 ack）
消费者：删除对应缓存（失败自动重试，删到成功为止）
```

**为什么它能解决"删缓存失败"这个核心痛点**：
1. Cache Aside 的失败点：删除是业务同步代码里的一步，失败就丢
2. Canal 方案：删除变成消费端的异步任务，**失败不丢**——MQ 持久化 + 消费端重试，删到成功为止

**可靠性怎么保证（面试讲这四点）**：
1. **binlog 不丢**：MySQL 写 binlog 与事务提交同步（sync_binlog=1），Canal 复用主从复制机制
2. **MQ 不丢**：消息持久化 + 消费成功才 ack
3. **消费端重试**：删除失败重试；删除是幂等操作（删不存在的 key 也算成功）
4. **删除幂等 + 最终兜底**：乱序消费影响可忽略，最终结果都是"删掉"，以最后一次为准

**不一致窗口还剩多大**：binlog 同步 + MQ 传输 + 消费耗时，秒级延迟——窗口期内读到旧值，**短暂不一致**（远强于"删除失败"的永久不一致）。

**真的需要强一致怎么办（面试追问）**：
1. 读写加同一把锁（方案 5：加锁串行化）
2. 或缓存只做快照 / 展示用，一致性以 DB 为准
3. 标准答法：**没有免费的强一致**——业务区分"可容忍短暂不一致"与"必须强一致"，前者用 Canal，后者放弃缓存或加锁

# 过期/淘汰策略

## 过期删除三种策略

key 设置了 TTL，到期后需要从内存中清除，Redis 在三种删除策略中做了取舍。

**答：用惰性删除 + 定期删除的组合，不用定时删除。**

1. **定时删除**

   - 做法：设置 TTL 的同时创建**定时器**，时间一到立刻删除
   - 结果：内存释放最及时，过期 key 不占内存
   - 代价：**CPU 开销爆炸**——海量 key = 海量定时器，单线程还要处理定时器到期事件，阻塞主流程
   - 结论：**Redis 不用**。100 万个 key 配 100 万个定时器，性能不可接受

2. **惰性删除**

   - 做法：**不主动删**，每次访问 key 时才检查是否过期（`expireIfNeeded`），过期则删除并返回空
   - 结果：**CPU 最友好**，只处理被访问的 key
   - 代价：**过期 key 堆积占内存**——一直没被访问的过期 key 永远占着空间（内存泄漏感）
   - 结论：**Redis 用**，但单独用不行（垃圾堆积）

3. **定期删除**

   - 做法：**周期性地随机抽查**过期 key 并删除（`activeExpireCycle`），每次限制时间和数量
   - 参数（面试细节）：每 100ms 执行一轮（hz=10）；每轮抽查 20 个 key；若过期比例 > 25% 继续抽查，直到低于阈值或超过时间预算
   - 结果：**CPU / 内存折中**——垃圾会被慢慢清掉，又不全库扫描阻塞主流程
   - 代价：有清理延迟，抽不到的 key 会残留（残留的过期 key 由惰性删除兜底）
   - 结论：**Redis 用**

**Redis 实际组合：惰性删除 + 定期删除**

```
惰性删除：保证"被访问的过期 key"一定被删（无延迟）
定期删除：保证"不被访问的过期 key"也会被慢慢清掉（防内存堆积）
定时删除：CPU 代价太大，淘汰 ✗
```

**对比表**

| 策略 | 触发时机 | CPU | 内存 | Redis 是否使用 |
|------|---------|-----|------|---------------|
| 定时删除 | key 过期那一刻（定时器） | 开销大 | 释放最及时 | ✗ |
| 惰性删除 | 访问 key 时 | 最省 | 过期 key 堆积 | ✓（组合之一） |
| 定期删除 | 周期抽查（每 100ms） | 适中 | 慢慢清理 | ✓（组合之一） |

## 八大淘汰策略

内存满了（达到 maxmemory），新的写入需要淘汰部分 key 腾出空间。

**答：noeviction + 3 个 allkeys + 4 个 volatile，共 8 种。**

```
noeviction      不淘汰，写入直接报错（默认策略）
    ↓ 要不要保护"没设 TTL 的 key"？
allkeys-*       从所有 key 里挑：lru / lfu / random
volatile-*      只从设置了 TTL 的 key 里挑：lru / lfu / random / ttl
```

**速查表**

| 策略 | 淘汰范围 | 选谁淘汰 | 典型场景 |
|------|---------|---------|---------|
| noeviction | 不淘汰 | - | 宁写失败不丢数据 |
| allkeys-lru | 所有 key | 最久没用 | 通用缓存（最常用） |
| allkeys-lfu | 所有 key | 最不常被用 | 访问频率稳定的场景 |
| allkeys-random | 所有 key | 随机 | 冷热均匀的数据 |
| volatile-lru | 有 TTL 的 key | 最久没用 | 只淘汰可过期的缓存 |
| volatile-lfu | 有 TTL 的 key | 最不常被用 | 同上 |
| volatile-random | 有 TTL 的 key | 随机 | 同上 |
| volatile-ttl | 有 TTL 的 key | 剩余 TTL 最短 | 快过期的先踢 |

**和过期删除的区别（易混点，必考）**：

| | 过期删除（惰性 + 定期） | 内存淘汰（maxmemory-policy） |
|--|----------------------|---------------------------|
| 触发条件 | key 的 TTL 到期 | 内存达到 maxmemory |
| 作用对象 | 设置了 TTL 的 key | 所有 key（allkeys）或有 TTL 的 key（volatile） |
| 目的 | 到期数据不让读 | 腾内存继续写 |

**一句话总结**：**过期删除管"到期"，内存淘汰管"满了"；两者独立，淘汰策略默认 noeviction，缓存场景一般配 allkeys-lru**

## LRU 原理与近似 LRU

LRU 是最常用的淘汰算法，这里讲它的底层实现原理，以及 Redis 为什么不用精确 LRU、近似 LRU 怎么做的。

**LRU vs LFU（先区分两个概念）**：
1. LRU 看"多久没用"：一次批量扫描会让热 key"看起来刚被用过"，污染统计
2. LFU 看"用得多不多"：计数器 + 衰减因子，抗扫描污染，更准
3. **Redis 的 LRU 是近似 LRU**：不维护全局时间序，采样（默认 5 个，`maxmemory-samples`）里挑一个淘汰——省内存和时间，效果接近精确 LRU

**LRU 底层实现原理（标准 LRU = HashMap + 双向链表）**

```
HashMap<key, 节点指针>           双向链表
                            头（最近使用）── ... ── 尾（最久未使用）
```

1. 访问 key（GET / SET）：HashMap 找到节点 → 摘下来移到链表头，O(1)
2. 新增 key：插到链表头 + 写 HashMap，O(1)
3. 淘汰：内存满 → 删链表尾节点 + 删 HashMap 对应项，O(1)

**核心**：每次访问都要"移动节点"，链表全局有序——精确但昂贵。

**为什么 Redis 不用标准 LRU**：
- 内存：每个 key 多维护 2 个指针（prev / next），百万 key 内存翻倍
- 写开销：每次访问都要移动链表节点
- 所以换近似 LRU：省内存省时间，效果接近

**Redis 近似 LRU 怎么做的（采样淘汰 + 淘汰池）**

1. 每个 key 的 redisObject 里存 **24bit 的 lru 字段**（秒级时间戳，约 194 天回绕，有回绕处理）
2. 淘汰时**不扫描全库**：随机采样 N 个 key（`maxmemory-samples`，默认 5），挑 lru 最小的淘汰
3. 3.0 起加**淘汰池（eviction pool）**：采样结果进大小为 16 的池子，每次从池中淘汰最旧的——池子保留多次采样的历史候选，淘汰更接近全局 LRU

```
内存满：
随机采样 5 个 → 和淘汰池（16 个）合并 → 淘汰 lru 最小的
→ 最旧候选留在池里 → 效果接近精确 LRU，代价只有 O(5)
```

**对比表**

| | 精确 LRU | Redis 近似 LRU |
|--|---------|---------------|
| 数据结构 | HashMap + 双向链表 | dict + 24bit lru 字段 |
| 每次访问 | 移动链表节点 | 更新时间戳字段 |
| 淘汰逻辑 | 删链表尾 | 采样 5 个 + 淘汰池挑最旧 |
| 内存开销 | 每 key 2 个指针 | 3 字节 |
| 精确度 | 100% | 接近精确 LRU |

**面试记忆点**：
1. 精确 LRU 的核心是"访问即移动"——双向链表保证 O(1) 移动和淘汰
2. 近似 LRU = 24bit 时间戳 + 随机采样 + 淘汰池，调大 `maxmemory-samples` 更准但淘汰更慢
3. 4.0 起 24bit 字段被 LFU 复用（低位计数、高位时间），一个字段支持两种策略

## 过期键与主从同步

过期 key 在真正删除前会一直占着内存；主从架构下，过期删除需要主从同步才能保证数据一致。

**答：会占用。过期只是"逻辑标记"，key 还留在 dict 里占着内存，直到被惰性删除或定期删除真正清掉。**

1. 惰性删除：只有 key 被访问时才会物理删除
2. 定期删除：每 100ms 随机抽查，抽不到的过期 key 继续占内存
3. 所以大量过期 key 堆积会白白占用内存 → 触发内存淘汰策略兜底（见上节八大策略）

**主从间过期怎么同步（面试重点）**：

```
主节点：惰性 / 定期删掉过期 key
    ↓ 向从节点广播 DEL 命令
从节点：收到 DEL 才物理删除
```

1. **删除只发生在主节点**：主节点通过惰性 + 定期删除过期 key，删除后向从节点广播 DEL 命令，从节点执行同样的删除——保证主从数据一致
2. **从节点不主动删**：从节点不执行定期删除，也不会对过期 key 做物理删除（读到过期 key 时逻辑上返回空，但物理上留着等主节点 DEL）——如果从节点各自删，复制延迟下主从会不一致
3. **从节点提升为主节点后**：先主动清理"逻辑过期但没删"的 key，再对外服务

**过期 key 与持久化（补充）**：
- RDB：保存快照时不写已过期的 key
- AOF：key 过期时追加 DEL 命令，重启后不会"复活"

**一句话总结**：**过期 key 会占内存直到被删；删除由主节点统一发起，从节点被动收 DEL，切换为主后自己清一次**

# 持久化

## RDB 原理、触发方式与优缺点

RDB 是 Redis 默认的持久化方式，把某一时刻的内存数据全量写成快照文件。

**答：RDB = 内存快照，把某一时刻全部数据写入二进制 dump.rdb 文件。**

**原理（fork + 写时复制 COW）**：

1. 主进程 fork 出子进程
2. 子进程把当前内存数据写入临时 RDB 文件，写完后原子替换旧文件,释放未被主进程引用的页表数据
3. fork 后主进程继续服务；期间的修改走 COW——主进程复制被修改的内存页，快照里仍是 fork 时刻的数据

```
主进程 ──fork──> 子进程（写 RDB 文件）
   │
   └─ 继续处理请求，修改的页复制一份（COW），不影响快照
```

**触发方式**：

1. 手动 `BGSAVE`（fork 后台执行，推荐）；`SAVE`（同步阻塞，不推荐）
2. 自动：配置 `save m n`——m 秒内有 n 次写操作就触发 BGSAVE
3. 正常关闭：shutdown 时自动保存

**优缺点**：

1. 优点：文件小、恢复快（二进制直接加载）；fork 子进程写盘，不阻塞主流程
2. 缺点：**两次快照之间的数据可能丢失**（如 5 分钟一次快照，崩溃丢最近 5 分钟）；fork 大实例有瞬时开销（COW 复制内存页）

## AOF 原理与三种日志刷写策略

AOF 记录每一条写命令，重启时重放命令恢复数据，比 RDB 丢数据少。

**答：AOF = 追加写命令日志，恢复时重放 appendonly.aof 里的命令。**

**原理**：每条写命令 → 追加到 aof_buf → 按刷写策略写盘 → 恢复时按顺序重放

**三种刷写策略（appendfsync 参数）**：

1. `always`：每条写命令都 fsync 落盘——最安全，最多丢 1 条，性能最差
2. `everysec`：每秒 fsync 一次——折中，最多丢 1 秒，**默认配置**
3. `no`：交给操作系统决定刷盘时机——性能最好，崩溃可能丢较多数据

| 策略       | 刷盘时机   | 最多丢失  | 性能     |
| -------- | ------ | ----- | ------ |
| always   | 每条命令   | 1 条命令 | 最差     |
| everysec | 每秒     | 1 秒数据 | 折中（默认） |
| no       | 操作系统决定 | 较多    | 最好     |

## AOF 重写机制原理与原因

AOF 文件只增不减会无限膨胀，重写机制把文件压缩成最小命令集。

**答：AOF 重写 = 基于当前内存数据重新生成最小 AOF 文件（每个 key 只留最终状态）。**

**为什么要重写**：

1. AOF 只增不减：同一 key 被 SET 100 次，文件里就 100 条命令，启动要重放 100 次
2. 文件膨胀 → 占磁盘空间 + 启动恢复变慢

**原理（不是重放旧文件，是读当前内存状态）**：

1. fork 子进程
2. 子进程用当前内存数据生成最小命令集
3. 重写期间的写命令进 AOF 重写缓冲区，完成后追加进新文件
4. 原子替换旧 AOF 文件

```
旧 AOF：SET k 1 / SET k 2 / ... / SET k 100（100 条）
重写后：SET k 100（1 条）——只保留最终状态
```

**触发**：手动 `BGREWRITEAOF`；自动由 `auto-aof-rewrite-percentage` + `auto-aof-rewrite-min-size` 控制

## RDB 与 AOF 对比及适用场景

RDB 快照和 AOF 日志是两种完全不同的持久化思路，各有所长。

**答：RDB 是快照（体积小、恢复快、易丢数据），AOF 是日志（记录全、恢复慢、更完整）。**

|       | RDB        | AOF               |
| ----- | ---------- | ----------------- |
| 记录内容  | 内存快照（二进制）  | 写命令日志（文本）         |
| 文件大小  | 小          | 大（靠重写控制）          |
| 数据完整性 | 丢两次快照间数据   | 最多丢 1 秒（everysec） |
| 恢复速度  | 快（直接加载）    | 慢（重放命令）           |
| 可读性   | 二进制不可读     | 文本可读、可修复          |
| 对性能影响 | fork + COW | 刷盘策略影响写性能         |

**适用场景**：

1. RDB：可容忍分钟级丢失的缓存场景、需要快速恢复、冷备传输
2. AOF：不能丢数据的业务数据、每次写入都要求可靠的场景
3. 最佳实践：**两个都开**——RDB 快速恢复 + AOF 保证完整性；重启时优先用 AOF 恢复

## 混合持久化原理（RDB + AOF）

4.0 引入混合持久化，把 RDB 的快与 AOF 的完整合二为一。

**答：AOF 文件头部是 RDB 全量快照，后面追加增量写命令——恢复快 + 丢数据少。**

**为什么混合**：

1. 纯 RDB：恢复快但丢数据多（两次快照之间全丢）
2. 纯 AOF：丢数据少但恢复慢（全量重放命令）
3. 混合：RDB 部分直接加载（快），增量部分重放（少）

**原理**：

1. 开启 `aof-use-rdb-preamble yes`（4.0 起默认开启）
2. AOF 重写时，先写 RDB 格式的全量快照（文件头），再把重写期间的增量命令以 AOF 格式追加在后面
3. 恢复时：先加载 RDB 部分，再重放 AOF 增量部分

```
混合 AOF 文件：
[ RDB 全量快照 ] + [ 增量写命令 ]
  直接加载（快）      重放（少）
```

**一句话**：快照打底 + 日志增量，恢复速度和数据完整性两头都占

## Redis 宕机后数据恢复流程

宕机重启后，Redis 靠持久化文件把数据恢复到内存。

**答：重启时优先加载 AOF（数据更完整），没有 AOF 再加载 RDB。**

**流程**：

1. 启动时检查持久化配置和文件：appendonly 开启且有 AOF 文件 → 加载 AOF
2. AOF 是混合格式 → 先加载头部 RDB 快照，再重放增量命令
3. 没有 AOF → 找 dump.rdb 直接加载
4. 加载完成对外服务；文件损坏可用 `redis-check-aof` / `redis-check-rdb` 修复

**为什么优先 AOF**：AOF 最多丢 1 秒数据，RDB 可能丢分钟级；RDB 只在 AOF 关闭或不存在时兜底

**面试记忆**：**AOF 优先、RDB 兜底
