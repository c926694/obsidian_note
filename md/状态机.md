# RCS 状态机与状态流转设计

> 记录当前 RCS 微服务中四处「状态变化」设计：任务状态机（task 域）、告警处置状态机（audit 域）、控制面文档修订链（document 域）、任务组与子任务状态机（orchestrator + dispatch 域）。
> 编排域的中文状态枚举定义在 `rpc/orchestrator/internal/model/status.go` 与 `rpc/orchestrator/internal/model/taskgroup.go`，调度域同值定义在 `rpc/dispatch/internal/store/store.go`；两边通过同一个库的 `rcs_task` / `rcs_task_group` 衔接，没有互相调用的 RPC。
> 约定源头：`rpc/*/*.proto`（对外接口）+ `rpc/*/internal/model`（状态机代码）。

---

## 1. 任务状态机（task 域）

### 1.1 状态枚举（9 个英文状态，入库英文字面量）

| 状态          | 含义                      |
| ----------- | ----------------------- |
| PENDING     | 任务已创建，等待受理             |
| ACCEPTED    | 校验通过，等待调度派单             |
| DISPATCHING | 已派单，等待设备执行（openTCS 调度中） |
| EXECUTING   | 车辆开始搬运                  |
| PAUSED      | 执行中被人工暂停                |
| EXCEPTION   | 执行中出现异常，等待人工处置          |
| COMPLETED   | 任务正常执行完毕（终态）            |
| FAILED      | 任务失败或因故中止（终态）           |
| CANCELLED   | 任务在完成前被取消（终态）           |

### 1.2 迁移矩阵（UpdateTask 校验，CanTransitionTo）

| 当前状态                           | 允许流转到                                       |
| ------------------------------ | ------------------------------------------- |
| PENDING                        | ACCEPTED、CANCELLED                          |
| ACCEPTED                       | DISPATCHING、CANCELLED                       |
| DISPATCHING                    | EXECUTING、EXCEPTION、FAILED、CANCELLED        |
| EXECUTING                      | PAUSED、EXCEPTION、COMPLETED、FAILED、CANCELLED |
| PAUSED                         | EXECUTING、FAILED、CANCELLED                  |
| EXCEPTION                      | EXECUTING、CANCELLED                         |
| COMPLETED / FAILED / CANCELLED | 终态，禁止再流转                                    |

### 1.3 处置动作与目标状态唯一映射（TaskAction → AfterState）

| action    | 含义        | 对应 after_state |
| --------- | --------- | -------------- |
| ACCEPT    | 受理        | ACCEPTED       |
| DISPATCH  | 派单        | DISPATCHING    |
| EXECUTE   | 开始执行      | EXECUTING      |
| PAUSE     | 暂停        | PAUSED         |
| RESUME    | 恢复        | EXECUTING      |
| EXCEPTION | 异常        | EXCEPTION      |
| COMPLETE  | 完成        | COMPLETED      |
| FAIL      | 失败        | FAILED         |
| CANCEL    | 取消        | CANCELLED      |

注：action 传了必须与 after_state 对应（如 ACCEPT→ACCEPTED），否则 40001；action 可空。

### 1.4 流转机制（UpdateTask）

- **入口**：`PUT /api/tasks/:id`
- **乐观锁**：version 列（初始 0，每次流转 +1），`WHERE version = 调用方传入值` 原子裁决；不匹配 → 40901「任务版本已过期」。**为什么需要 version**：迁移矩阵存在**环**（EXECUTING⇄PAUSED 可来回流转），状态能绕回原点——旧请求的重放会"复活"（重新匹配成功），需要 version 单调递增作绝对时间线裁决。多路汇聚（如三态都可到 FAILED）只是附带特征，不破坏 status 裁决本身。
- **事务双写**：task_state 投影（business_state、version+1、updated_at）+ task_state_event 账本一条（before_state 由服务端事务内读取，调用方不可传），sequence 由服务端行锁下 `MAX+1` 分配。
- **防重放**：同一请求发第二次，version 已 +1，必然 40901。
- **错误语义**：不存在 40401；非法迁移/动作不一致 40001；版本过期 40901；终态再流转 40901。

## 2. 告警处置状态机（audit 域）

### 2.1 状态枚举（4 值英文，入库英文字面量）

| 状态           | 含义               |
| ------------ | ---------------- |
| ACTIVE       | 告警存在且无人处置        |
| ACKNOWLEDGED | 已确认，有人受理处置中      |
| RESOLVED     | 已解决，告警原因已消除，等待关闭 |
| CLOSED       | 已关闭，处置COMPLETED（终态）     |

### 2.2 迁移矩阵（严格链式，UpdateAlert 校验）

```
ACTIVE → ACKNOWLEDGED → RESOLVED → CLOSED
```

一步不能跳、不可回退：ACTIVE 只能到 ACKNOWLEDGED，ACKNOWLEDGED 只能到 RESOLVED，RESOLVED 只能到 CLOSED，CLOSED 终态禁止再处置。矩阵外组合（含自身）一律拒绝。

### 2.3 动作枚举（两种，含义不同）

| 处置动作（UpdateAlert 请求，AlertHandleAction） | 账本动作（audit_alert_lifecycle_event.action，AlertAction） |
|---|---|
| ACKNOWLEDGE（确认） | ACKNOWLEDGED |
| RESOLVE（解决） | RESOLVED |
| CLOSE（关闭） | CLOSED |
| —（触发通道） | RAISED（告警触发） |

### 2.4 触发语义（RaiseAlert，内部 rpc 写入口）

同一条 alert_key 反复触发时三分支处理：

| 当前状态 | 处理 | 账本 |
|---|---|---|
| key 不存在 | 新告警：插投影（occurrences=1、status=ACTIVE） | 写 RAISED（from=NULL，sequence=1） |
| 已 CLOSED | **重新激活并清零**：status 回 ACTIVE、occurrences=1、first_seen_at 刷新、assignee/三个处置时间戳清空 | 写 RAISED（from=CLOSED，sequence=MAX+1） |
| 其他（还挂着） | 归并：occurrences+1、刷新 last_seen_at/message | **不写账本**（生命周期未前进） |

请求中的 occurrences/status 由服务端按上述语义计算，忽略调用方传入值。

### 2.5 处置机制（UpdateAlert）

- **入口**：`PUT /api/alerts`（alert_key 走 body）
- **裁决方式**：`WHERE status = 前置状态` 原子更新。**为什么不加 version 列**：严格链式单向、每个状态仅一个合法后继，当前状态本身就携带完整版本信息——重放时状态已前进被矩阵（含自身）拒绝，双人并发只有一人 UPDATE 成功。与 task 不同，无需额外列。
- **事务双写**：audit_active_alert 投影（status、按动作写入 acknowledged_at/resolved_at/closed_at、assignee、last_actor/last_reason）+ audit_alert_lifecycle_event 账本一条（from_status 服务端事务内读取），sequence 行锁下 `MAX+1`。
- **错误语义**：不存在 40401；跳步/重放 40001「非法状态迁移」；并发被抢先 40901「告警状态已变化」；CLOSED 再处置 40901「告警已关闭」。

## 3. 控制面文档修订链（document 域）

不是状态机，而是**单调递增的修订号链**：

- **revision**：从 1 起，每次 `PUT /api/documents/:type/:id`（ReplaceDocument）服务端 +1，同 key 的旧 revision 不再更新（只读历史）。
- **事件类型**（control_plane_document_event.event_type）：`CREATED`（创建，revision=1）/ `REPLACED`（替换，revision+1）；`MIGRATED`（迁移导入，已实现——迁移三路分支中"新建/替换"都会写入该事件）。`ROLLED_BACK` 保留定义但回滚实现为"清事件后删文档"（外键约束所致，批次级审计由 run/item 台账保留）。
- **内容唯一性**：content_sha256 记录每次内容摘要，同 revision 内容不可变。
- **读写**：文档只有创建与替换两个动作，无「删除」——旧版本靠 revision 保留。

## 4. 任务组与子任务状态机（orchestrator + dispatch 域）

### 4.1 状态枚举（中文，入库字面量）

| 状态 | 含义 |
| --- | --- |
| 已创建 | 建组后、生成子任务前（保留定义；当前实现建组即写「待下发」） |
| 待下发 | 子任务已生成，等调度派车（组与子任务都用这一档） |
| 待执行 | 已下发给执行系统、等车接；当前主要出现在**任务组**上（继续任务时组置回这一档） |
| 执行中 | 车已开始执行（调度派发成功时回填车号与开始时间） |
| 已暂停 | 非终态挂起：本组按配置停在某段，后续子任务停在「待下发」，等「继续任务」放行 |
| 已完成 / 已取消 / 失败 | 终态 |
| 已跳过 | 子任务专用终态：分支跳变或入口之前被跨过的节点，不派发、也不阻塞组收尾 |

### 4.2 迁移矩阵

| 当前 | 允许流转到 |
| --- | --- |
| 待下发（子任务） | 执行中（调度派发成功）、已跳过（分支跨过）、已取消、失败 |
| 待下发（组） | 执行中、已暂停、已取消、失败、已完成 |
| 执行中 | 已完成、已取消、失败 |
| 已暂停（组） | 待执行（继续）、已取消（取消） |
| 已完成 / 已取消 / 失败 / 已跳过 | 终态，不再流转 |

### 4.3 谁在什么时候写状态

| 时机 | 写什么 | 位置 |
| --- | --- | --- |
| 建组 | 组与子任务同事务写入，状态都是「待下发」；`start_at` 之前的动作写「已跳过」 | 编排域 `createtaskgrouplogic.go` |
| 派发成功 | 子任务置「执行中」并回填 `agv_code` 与开始时间；组同步推进 | 调度域 `store.go`、`scheduler.go` |
| 每段收尾 | 子任务置「已完成」或「失败」，回填当前位置、结束时间、失败原因 | 调度域 `store.go` |
| 本段配了「不继续任务」且组内还有后续子任务 | 组置「已暂停」，且**不再推进组状态**；后续子任务留在「待下发」 | 调度域 `sched/pausegroup.go` |
| 分支跳变 | 跨过的节点置「已跳过」 | 调度域 `store/branch.go` |
| 组内没有未完成子任务 | 组推进到「已完成」（或「已取消」「失败」） | 调度域 `store.go` |
| 继续任务 | 只有「已暂停」能继续（否则 40901）；组置「待执行」，子任务仍按「待下发」被调度派发 | 编排域 `continuetaskgrouplogic.go` |
| 取消任务组 | 组已是终态则 40901；组内未完成子任务一并置「已取消」；组置「已取消」并回填结束时间 | 编排域 `canceltaskgrouplogic.go` |

### 4.4 判定与并发

- **派发过滤**：子任务状态为「待下发」、所属组未处于「已暂停」、且组内串行（前序子任务未到终态就不派）。
- **组收尾**：调度侧按「组内是否还有未完成子任务」判定，一句 SQL 裁决，不缓存计数。
- **挂起期间**：组状态保持「已暂停」，调度不推进它，也不派发后续子任务。
- **终态集合**：编排侧为「已完成 / 已取消 / 失败」；调度侧把「已跳过」一并算作终态（不派发、不阻塞收尾）。
- 这两张表用**条件更新**推进状态，没有 version 列：派发与收尾都由「当前状态 + 组内进度」这两条前提裁决，重复推进会在条件上不匹配。

## 5. 两种乐观锁对照（设计要点）

| 维度    | task（任务状态）                      | audit（告警处置）                         |
| ----- | ------------------------------- | ----------------------------------- |
| 裁决依据  | version 列，`WHERE version = 传入值` | status 列，`WHERE status = 前置状态`      |
| 为什么   | 矩阵有**环**（EXECUTING⇄PAUSED 可来回流转），状态能绕回原点，重放会复活，需 version 作绝对时间线 | 严格链式**无环单向**，每状态一生最多经过一次，status 自带单调性即裁决键 |
| 重放表现  | 40901「版本已过期」                    | 40001「非法状态迁移 X -> X」                |
| 并发被抢先 | 40901「版本已过期」                    | 40901「状态已变化」                        |
| 表结构代价 | version 列（schema 自带）            | 无额外列                                |

选择依据：**状态机形状决定裁决方式**——有环用版本号，无环用当前状态（无环时即使有跳步/多路汇聚，status 裁决依然安全：每个状态最多经过一次，重放永远匹配不上）。

## 6. 共性设计原则

1. **投影 + 账本同事务双写**：状态变化必留一条事件，要么都成功要么都失败（defer Rollback + 末尾 Commit）。
2. **sequence 服务端分配**：`UPDATE` 成功后（行锁保护下）`COALESCE(MAX(sequence), 0) + 1`，并发不撞号，历史链条不缺号。
3. **before/from 调用方不可传**：由服务端事务内无锁 SELECT 前置读取，正确性由 UPDATE 成功保证。
4. **终态不可再流转**：IsTerminal 前置拦截（完成/失败/CANCELLED、CLOSED）。
5. **参数校验三层防线**：拦截器 proto 注解（Protovalidate：格式/长度/必填）→ logic 域枚举与一致性 → model 读库业务规则。
